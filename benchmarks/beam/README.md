# BEAM benchmark harness

Runs [BEAM](https://github.com/mohammadtavakoli78/BEAM) — *"Beyond a Million
Tokens: Benchmarking and Enhancing Long-Term Memory in LLMs"* (Tavakoli,
Salemi, Ye, Abdalla, Zamani, Mitchell; [arXiv:2510.27246](https://arxiv.org/abs/2510.27246),
ICLR 2026) — against fishmem, scored under the **official BEAM evaluation
protocol** ported from the paper repo:

- `src/prompts.py` → [`prompts.ts`](./prompts.ts) (generated byte-for-byte:
  `unified_llm_judge_base_prompt`, `answer_generation_for_rag`, the
  `llm_equivalence` classifier messages)
- `src/evaluation/compute_metrics.py` + `run_evaluation.py` + `report_results.py`
  → [`judge.ts`](./judge.ts) (rubric-nugget judging, event-ordering alignment +
  Kendall tau-b, official aggregation)
- official judge model: **`gpt-4.1-mini`, temperature 0** (`src/llm.py`)

> Naming: mem0's blog expands BEAM as "Benchmark for Evaluating Agent Memory";
> the paper's own title is "Beyond a Million Tokens" (its §2 heading reads
> "BEnchmarking memory cApabilities of LLMs"). Same benchmark.

## Dataset

100 LLM-generated but human-validated conversations across four token tiers,
with **20 probing questions per conversation** (2 per category) spanning ten
memory abilities: `abstention`, `contradiction_resolution`, `event_ordering`,
`information_extraction`, `instruction_following`, `knowledge_update`,
`multi_session_reasoning`, `preference_following`, `summarization`,
`temporal_reasoning`. Questions probe **writing, updating, and reading
memories under ambiguity and changing facts**; each carries a `rubric` — a
list of atomic criteria ("nuggets") that the official judge scores one by one.

| tier (`--variant`) | conversations | questions | chat.json total | per-file max |
|---|---|---|---|---|
| `100k` (paper calls it 128K) | 20 | 400 | ~13MB | ~1MB |
| `500k` | 35 | 700 | ~84MB | ~3.7MB |
| `1m` — mem0's "BEAM 1M" | 35 | 700 | ~174MB | ~7.9MB |
| `10m` — mem0's "BEAM 10M" | 10 | 200 | ~528MB | ~64MB |

**License**: dataset **CC BY-SA 4.0**, code **MIT** (per the repo README).
Publicly downloadable, no auth/gating, from either:

- GitHub (per-conversation JSON, the layout this harness reads):
  <https://github.com/mohammadtavakoli78/BEAM> under `chats/<TIER>/<n>/`
- HuggingFace (parquet; needs the official Python converter
  `src/beam/download_dataset.py`):
  [Mohammadta/BEAM](https://huggingface.co/datasets/Mohammadta/BEAM) (100K/500K/1M, ~106MB)
  and [Mohammadta/BEAM-10M](https://huggingface.co/datasets/Mohammadta/BEAM-10M) (~344MB)

Place data under `benchmarks/beam/data/<TIER>/` (git-ignored), e.g. for the 1M tier:

```bash
git clone --depth 1 --filter=blob:none --sparse https://github.com/mohammadtavakoli78/BEAM /tmp/BEAM
git -C /tmp/BEAM sparse-checkout set chats/1M
mkdir -p benchmarks/beam/data
cp -R /tmp/BEAM/chats/1M benchmarks/beam/data/1M
```

Expected layout: `data/<TIER>/<n>/chat.json` +
`data/<TIER>/<n>/probing_questions/probing_questions.json` (exactly what the
repo / the official converter produce).

### Format

`chat.json` is a list of **batches**, each `{batch_number, time_anchor, turns}`
where `turns` is a list of message groups (`{role, id, content, time_anchor?,
question_type?}`); 10M files wrap batches in 10 sequential `{"plan-<n>": ...}`
objects, which the loader flattens. `probing_questions.json` maps each of the
ten categories to 2 question objects `{question, rubric: string[], difficulty,
...category-specific metadata}`.

## Official evaluation protocol (what judge.ts replicates)

1. Each rubric item is judged independently with the verbatim
   `unified_llm_judge_base_prompt`, which demands JSON
   `{"score": 1.0 | 0.5 | 0.0, "reason": ...}`.
2. Per-question score = mean over rubric items (`llm_judge_score` — this is the
   nugget-coverage number mem0's blog calls "Coverage").
3. `event_ordering` additionally splits the response into lines, aligns them
   against the rubric with the `llm_equivalence` binary classifier, and computes
   precision/recall/F1 plus normalized Kendall tau-b
   (`tau_norm = (tau_b + 1) / 2`, `final_score = tau_norm * f1`).
4. Official aggregation (`report_results.py`): per category, mean
   `llm_judge_score` — **except `event_ordering`, which reports `tau_norm`**.
   The headline "overall" is the macro average of the ten category scores
   (reported as `overallMacro`; `overallMicro` over questions is also printed).

Official quirks preserved (documented in `judge.ts`): the judge prompt's
`<question>` slot is **never substituted** by the official code (the judge
sees the literal text `<question>`); nine categories aggregate per-item scores
with Python `int()` (a 0.5 floors to 0), `event_ordering` with `float()`; the
official `extract_facts` call in `evaluate_event_ordering` is dead code
(immediately overwritten by `response.split("\n")`) and is skipped; a
NaN tau-b (constant ranks) maps to `tau_norm = 0`.

## Run

```bash
# Offline pipeline check (no API key, mock providers; covers rubric judging,
# the int() flooring path, event-ordering alignment + Kendall tau, and the
# <question>-slot quirk):
pnpm bench:beam -- --smoke

# Cheap real validation: 2 conversations of the smallest tier
pnpm bench:beam -- --systems fishmem,mem0 --variant 100k --instances 2 --split dev

# mem0-blog-comparable setups (read the cost section first!):
pnpm bench:beam -- --variant 1m --split full
pnpm bench:beam -- --variant 10m --concurrency 1 --split full

# Subscription-backed Codex answer run (publishable only after the full gate):
pnpm bench:beam -- --systems fishmem,mem0 --variant 100k \
  --instances 1 --split dev \
  --llm gpt-5.6-luna --write-reasoning none \
  --answer-provider codex-cli \
  --answer-model gpt-5.6-sol --answer-reasoning none \
  --codex-transport app-server
```

`OPENAI_API_KEY` is read from the environment or the repo-root `.env`;
`OPENAI_BASE_URL` (or `--base-url`) supports OpenAI-compatible proxies.
The key remains required for Codex answer runs because memory writes,
embeddings, and the official judge stay on their configured compatible API provider. See the shared
[answer provider policy](../README.md#answer-provider-policy).

### Flags

| flag | default | meaning |
|------|---------|---------|
| `--variant 1m\|10m\|100k\|500k` | `1m` | dataset tier |
| `--split dev\|holdout\|full` | required | disclosure written into result JSON |
| `--instances N` | all | run only the first N conversations |
| `--categories a,b,c` | all | filter the ten question categories |
| `--concurrency N` | 2 | conversations processed in parallel (sequential within) |
| `--top-k N` | 10 | memories retrieved per question |
| `--chunk-size N` | 4 | conversation messages per `add()` call |
| `--profile-every N` | 5 | `endSession()` (profile refresh) every N batches; 0 disables |
| `--llm MODEL` | `gpt-4o-mini` | memory-write model and default answer model |
| `--write-reasoning LEVEL` | off | explicit write/extraction reasoning effort for supported models |
| `--answer-model MODEL` | = `--llm` | override the answering model only |
| `--answer-provider NAME` | `openai-chat` | `openai-chat`, `openai-responses`, or version-pinned `codex-cli` |
| `--answer-reasoning LEVEL` | off | Responses/Codex reasoning effort; Codex does not accept `max` |
| `--codex-path PATH` | `CODEX_PATH` or `codex` | Codex CLI binary; app-server requires CLI >= 0.144.0 |
| `--codex-transport NAME` | `exec` | `exec` or preferred persistent `app-server` |
| `--embedder MODEL` | `text-embedding-3-small` | embedding model |
| `--judge MODEL` | `gpt-4.1-mini` | judge model (official BEAM default) |
| `--provider-timeout-ms N` | `120000` | deadline per provider attempt |
| `--operation-timeout-ms N` | `300000` | deadline for a complete adapter `add`/`search` |
| `--provider-retries N` | `2` | retries for an individual provider request |
| `--operation-retries N` | `0` | retries of a complete adapter operation |
| `--system fishmem\|mem0` | `fishmem` | run one memory system |
| `--systems a,b` | - | run multiple systems into one paired result file |
| `--resume` | off | resume per-system conversation checkpoints for the same output path |
| `--out PATH` | `benchmarks/results/beam-<ts>.json` | results JSON |
| `--smoke` | off | offline mock run with 2 fabricated conversations |

Each conversation is fully isolated: a fresh in-memory adapter with
`userId = beam_<tier>_<id>`; every batch is ingested as chunked `add()` calls
with the batch `time_anchor` prefixed to the first message of each chunk.
Answers use the **official** `answer_generation_for_rag` prompt with the
retrieved memories as `<context>` (the official RAG baseline protocol, k=5
dense retrieval over USER/ASSISTANT pair chunks — here the memory system
replaces the retriever, which is the point of the comparison).

## Cost guidance (rough; gpt-4o-mini memory writes/answering, gpt-4.1-mini judge)

Ingestion embeds every conversation chunk. Write-side LLM cost only applies to
systems/overrides that enable derivation or extraction; use emitted token
accounting from a partial run before extrapolating.

- **100k**: ~2M chat tokens, 400 questions → roughly **$2–5**. Start here.
- **1m**: ~37M chat tokens, 700 questions, ~1.9K judge calls → roughly
  **$20–40** and several hours at `--concurrency 2`.
- **10m**: ~100M chat tokens, 200 questions → roughly **$50–110**, long wall
  clock, and ~64MB JSON files (raise heap:
  `NODE_OPTIONS=--max-old-space-size=8192`). Use `--instances 1` first.

Judging adds ~2.7 rubric items/question plus, for event-ordering, one
alignment call per (response line × unused rubric item) pair. Always do a
`--instances 1` dry run and extrapolate from the printed ingest totals before
committing to a full tier.

For resumed runs, `successfulOperationMs` sums the recorded ingest, search,
answer, and judge durations of successful checkpointed conversations.
`invocationWallClockMs` covers only the current process and is accompanied by
`resumedUnits`/`freshUnits`; it is not a cross-resume performance metric.

## Comparison discipline

Our number is measured under the **official BEAM repo protocol** (verbatim
prompts, official aggregation, judge model disclosed via `--judge`, default
`gpt-4.1-mini`) with the full configuration written into the results JSON.

mem0's published BEAM numbers (**64.1** on BEAM 1M, **48.6** on BEAM 10M,
"Coverage" metric) are **self-reported** figures produced by their own harness
([mem0ai/memory-benchmarks](https://github.com/mem0ai/memory-benchmarks)),
which uses an **adapted** judge prompt (restructured wording; unlike the
official script it substitutes the actual question into the prompt) and their
platform's retrieval configuration. The third-party
[AMB leaderboard](https://agentmemorybenchmark.ai) (vectorize-io) also runs
BEAM data under its own harness. Cite all of those as their respective claims;
do **not** present them as directly comparable to numbers produced here. The
only apples-to-apples comparison is between runs of this harness with
disclosed, identical configs.
